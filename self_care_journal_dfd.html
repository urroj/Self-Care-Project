LEVEL 2 — DETAILED DATA FLOWS (PER MODULE)
EVERY INPUT, TRANSFORMATION, STORAGE, AND OUTPUT FOR EACH SUBSYSTEM
P1 · CYCLE TRACKER
INPUTS
User→ P1.1 Start Cycle start_date, period_start, period_end (opt), notes
User→ P1.2 Log Day log_date, flow_intensity(0-5), mucus_type, moods[], 9×bool symptoms, sleep_hours, sleep_quality(1-3), stress_level(1-3), weight_kg, exercise_mins
User→ P1.3 Save Dates cycle_id, period_end, ovulation_date
User→ P1.4 Complete Cycle cycle_id, end_date
TRANSFORMATIONS
P1.2→ day_of_cycle = log_date − start_date + 1 (computed in FastAPI before INSERT)
D1 cycles→ Generated cols cycle_length = end_date − start_date  |  period_duration = period_end − period_start + 1  |  luteal_length = end_date − ovulation_date
P1.2 check→ duplicate guard GET /api/logs → filter by log_date + cycle_id → if match exists: show confirmation, overwrite with ON CONFLICT DO NOTHING after confirm
STORAGE
P1.1→ D1 cycles INSERT new row, is_complete=FALSE
P1.2→ D2 daily_logs INSERT all symptom + lifestyle fields
P1.3→ D1 cycles UPDATE SET period_end=?, ovulation_date=? WHERE id=?
P1.4→ D1 cycles UPDATE SET end_date=?, is_complete=TRUE → triggers P2
OUTPUTS
D1+D2→ User: tabs cycle table (all columns + generated), daily logs table (filterable), stat cards (mean length, phase), phase progress bar, cycle_summaries view (avg flow/sleep/stress per cycle)
P2 · ML PIPELINE
INPUTS
Public CSVs→ P2.1 Setup Prior Fehring: LengthofCycle, Age, BMI, LutealPhase, MeanBleedingIntensity / mcPHASES: hormone levels, cycle boundaries, wearable signals
D1 cycles→ P2.2 Predict last N cycle_lengths, avg_sleep, avg_stress, avg_flow per cycle (from cycle_summaries view)
D6 saved_models→ P2.2/P2.3 population_prior.json (NB params + GBM weights), bayesian_state.json (alpha, beta posteriors), lstm_pretrained.pt + scaler.pkl
TRANSFORMATIONS (3 PHASES)
Phase 1 (0-2)→ PopulationPrior Negative Binomial fit on irregular subset (std>7d or mean≥30d) → NB params (mu, r) + GradientBoosting point estimate from covariates
Phase 2 (3-7)→ Bayesian update Gamma(α,β) prior → posterior α'=α+Σy, β'=β+n → Negative Binomial predictive distribution → personal_weight = n/(n+β) grows 37%→87%
Phase 3 (8+)→ LSTM fine-tune 6-cycle lookback sequences → 2-layer LSTM → Huber loss (δ=2.0) → fine-tune at 0.2× LR → 100 MC Dropout passes → mean ± σ distribution
Features→ preprocessor.py rolling mean/std, last-3 mean/std, linear trend, deviation_from_mean, irregularity_flag, period_duration, avg_flow, avg_sleep, avg_stress
STORAGE + OUTPUTS
P2 result→ D3 model_runs INSERT { predictions: { point_estimate, ci_lower_80, ci_upper_80, next_period_start_est, ovulation_date_est, fertile_window_start/end, confidence, personal_weight }, model_phase, personal_cycles }
P2 result→ D6 saved_models WRITE updated bayesian_state.json + lstm_finetuned.pt (background thread)
D3 model_runs→ User: Results tab prediction cards, CI width trend chart (Insights), phase progress (Cycles tab), status bar next period date
P3 · JOURNAL
INPUTS
User→ P3.1 Navigate ◄/► buttons (offset ±1 day), date picker (jump to date), target always ≤ TODAY
User→ P3.2 Write Entry entry_date (current), weather (one of: sunny/cloudy/rainy/stormy/snowy/foggy or empty), content (free text)
TRANSFORMATIONS
P3.1 → D4→ load check GET /api/journal/{date} → last_saved≠null means entry exists → populate textarea + weather + show SAVED badge; last_saved=null → blank slate
savedEntry state→ dirty detection isDirty = (content ≠ savedEntry.content) OR (weather ≠ savedEntry.weather) → shows ● UNSAVED in title bar
save click→ overwrite guard if savedEntry≠null AND isDirty → show yellow confirmation banner → user must confirm YES before upsert proceeds
STORAGE + OUTPUTS
P3.2 save→ D4 journal_entries UPSERT INSERT ... ON CONFLICT (entry_date) DO UPDATE SET weather=?, content=?, updated_at=NOW()
D4→ User: JournalWindow entry content in textarea (persists after save), SAVED badge in header, LAST SAVED timestamp in footer, UPDATE button label (vs SAVE for new)
PostgreSQL→ Storage TEXT stored with TOAST compression — 10 years of daily entries < 10 MB on disk
P4 · ETF TRACKER
INPUTS
Yahoo Finance→ P4.1 Chart Data v8/finance/chart/{symbol}?interval=1h|1d&range=1wk|1mo|1y → timestamps[], closes[], opens[], highs[], lows[], regularMarketPrice, previousClose, currency, exchangeName
User→ P4.2 Add Investment symbol (ISWD.SW or IGDA.L), amount (ETF currency), investment_date, notes (optional)
TRANSFORMATIONS
P4.1→ chart normalise filter null closes, format timestamps to "YYYY-MM-DD HH:MM", round to 4dp, compute change = current − prev_close, change% = change/prev_close × 100
P4.2 price fetch→ historical lookup period1 = investment_date − 4 days, period2 = investment_date + 1 day, interval=1d → find closest close ≤ investment_date (handles weekends / bank holidays)
price_on_date→ units calc PostgreSQL GENERATED: units = amount / price_on_date (stored, recomputable)
live price × units→ portfolio calc current_value = Σ(units × current_price) · gain_loss = current_value − Σamount · return_pct = gain_loss / Σamount × 100 (computed in React, no extra API call)
STORAGE + OUTPUTS
P4.2 result→ D5 etf_investments INSERT { symbol, amount, investment_date, price_on_date, units(generated), notes }
D5 + live price→ User: ETFWindow line chart (1W/1M/1Y) with prev_close reference line · portfolio summary: total invested, current value, gain/loss ▲▼, return % · per-entry table: date|invested|price paid|units|current val|gain/loss · auto-refresh every 5 min
Route order→ ⚠ Critical note GET /api/etf/{symbol}/investments and POST /api/etf/investments MUST be registered BEFORE GET /api/etf/{symbol} in api/main.py — otherwise FastAPI treats "investments" as a symbol value and returns 405 Method Not Allowed
